# Проверка моделей кандидатов на работу

## Область и исходные требования

Оценивается представленная модель по конкретному тестовому заданию и критериям
проверяющего. Зафиксировать код работы/кандидата, версию задания и профиль
критериев по [criteria-contract.md](criteria-contract.md).
Для тестового задания АР также обязательно прочитать и применить
[уточнения задания АР](ar-assignment-clarifications.md), сохранив их версию
в профиле проверки. Они не распространяются автоматически на другие задания.
Для АР применять также [каталог весов ошибок](ar-error-weights.md).
Для КР применять [каталог весов ошибок КР](kr-error-weights.md).
Для локальных ошибок маркировки АР и КР применять
[область действия общего правила](local-marking-errors.md).
При неполном составе модельных элементов АР и КР применять
[общее правило отсутствующих экземпляров](missing-model-elements.md).
Для нового типа ошибки сначала спросить пользователя о категории значимости;
до ответа не назначать вес и не учитывать неизвестный вес в балле.
Имя, возраст, пол и другие не относящиеся к работе сведения не являются
критериями качества модели. Вывод о модели отделять от решения о найме.

Если критериев нет, собрать доступную инвентаризацию и перечислить данные,
нужные для оценки. Не выставлять балл, «сдал/не сдал» или нарушения по
придуманным требованиям. Предлагаемые критерии явно помечать как предложения.
Правила генерации семейств из `KPLN_RevitRules` автоматически не применяются:
их можно включить в профиль только с источником, версией и областью действия.

## Получение доказательств через общий мост

1. Вызвать `list_revit_sessions`, выбрать требуемый экземпляр по документу
   и версии Revit, затем `get_revit_context`. Зафиксировать `session_id`,
   `document_id`, `revision`, версию моста и время чтения. При неоднозначности
   документа уточнить выбор до чтения содержимого модели.
2. По каждому критерию определить необходимые данные и доступный инструмент.
   Получать только относящиеся к заданию категории, типы, экземпляры, параметры,
   виды и связи. Список связей не считать чтением содержимого связанных моделей.
3. Использовать `UniqueId`, ID категории и ID параметров из ответа.
   `document_id` действует в сессии; ID элементов хоста и связей нельзя смешивать.
   Значения экземпляров и типов читать и оценивать раздельно.
4. Обойти страницы до `next_offset=null`. Для согласованного набора требовать
   одинаковую `revision`; при её смене перечитать затронутый набор.
   Для общего отчёта заявлять одну ревизию только при согласованности всех
   снимков. Если её получить не удалось, отметить неполноту проверки.
5. Сохранить исходные ответы и происхождение данных в `local/<review-id>/`.
   В отчёте зафиксировать версии слоёв правил, точный профиль критериев,
   хеши профиля и снимков; ссылки на исходники не заменяют сохранённый профиль.
   Исходный файл модели хешировать только при его доступности; хеш файла
   на диске не доказывает совпадение с несохранённым открытым документом.

Double-параметры моста содержат внутренние единицы Revit, геометрические
габариты — миллиметры. Физическую величину устанавливать по метаданным;
не сравнивать исходный Double с нормативом в мм/кВт без преобразования.
`display_value` и округление не задают инженерный допуск. `null` не равен нулю.
Bounding box не доказывает точное пересечение, зазор или качество геометрии.
Для пространственных данных связей учитывать матрицу преобразования.

Наличие команды в документации не доказывает наличие всех требуемых полей.
Проверить фактическую схему/ответ моста. Если нет данных предупреждений,
коннекторов, точных тел или связей зависимостей — соответствующая проверка
получает `not_checked` с причиной и требуемым расширением чтения.
Не делать вывод об отсутствии дефекта из отсутствия API-данных.

## Выполнение проверки

### Коллизии: API по всей модели

Прямое указание пользователя от 2026-10-06 для АР и КР: использовать
check_intersections / check_revit_intersections, контракт 2 (мост >=1.0.11),
по всем 3D-элементам текущего документа. Не сужать область категориями,
выделением, видами или шестью категориями из прежней проверки АР.
Штатный диалог не запускать и не требовать его для подтверждения результата.

Сохранить размеры общей выборки и прочитанной геометрии, число проверенных
объёмных элементов, пары и все исключения/ошибки. Члены групп и скрытые
элементы входят в область; контейнеры групп не дублируют членов. Удалённые
из проверки 2D/служебные объекты и линии без объёма не являются пропущенными
твёрдыми телами, но их учёт сохраняется. Mesh, поверхности, недоступная
3D-геометрия, связи, закрытые РН и лимиты означают неполную проверку.
Нельзя представлять неполный нулевой результат как отсутствие коллизий.
Требуется complete=true и status=no_intersections. Пустая область не pass.
Обработку допустимых сопряжений и исключений выполняет профиль АР/КР,
мост возвращает исходные пары без оценки кандидата.

В официальном PDF писать «API-проверка коллизий всей модели: N объёмных
элементов, найдено M пересечений» только при полном результате. Для неполного
дать реальный охват и конкретную причину. Не включать фразу «штатный диалог
не запускался» как недостаток: API теперь согласованный способ проверки.
При этом не обещать проверки иных геометрических дефектов или возможностей,
которых нет в механизме Revit API (включая автоматически соединённые элементы).

Представленную модель читать без исправлений, создания типов, изменения
параметров, сохранения или синхронизации. Показ/выделение нарушений через
`select_revit_elements` допустим по запросу пользователя. Отдельно заказанное
исправление вести после фиксации исходного отчёта, с сохранением различия
между представленным кандидатом состоянием и исправленной версией.

Формальные сравнения выполнять детерминированно по критерию, единицам и
согласованному допуску. Содержательные суждения сопровождать объяснением и
доказательствами; неоднозначные случаи передавать на экспертную проверку.
Ошибку чтения/таймаут/неполную выборку не считать ошибкой кандидата.
В случае незавершённой операции чтения использовать `get_revit_operation`;
устаревший снимок не представлять как текущее состояние модели.

## Отчёт

Для АР и КР применять [интерпретацию оценки и обучения](score-training-policy.md).
Во всём диапазоне 0–10 указывать итоговую оценку с одним знаком после запятой
(например, 3,0/10; 6,7/10; 10,0/10), в чате и PDF. При округлении до десятых
использовать обычное десятичное округление: 6,25 → 6,3, без банковского округления.
Это точность представления экспертной оценки, не новая формула вычисления.
В PDF отражать требуемое обучение по согласованному диапазону; нерешённую
границу не превращать в автоматическое разрешение работы в основных файлах.

Основную часть отчёта АР и КР по умолчанию выдавать отдельным PDF,
пригодным для пересылки. Прямое указание пользователя от 2026-10-06.
Официальный, нейтральный стиль: без «бро», разговорных обращений, эмодзи
и переписки о настройке инструментов. В чате допустим привычный стиль,
но он не переносится в PDF. В чате — краткий итог и ссылка на документ.

PDF содержит наименование модели и раздел, дату фактической проверки,
версию ТЗ/профиля, итоговую оценку с указанием экспертного характера при
отсутствии формулы, таблицу основных замечаний с категориями и весами,
комментарий к полноте комплекта, выполненные требования, результаты и
область проверки пересечений, ограничения и статус дополнительной части.
Не помещать в пересылаемую сводку локальные пути, ключи сессий и прочие
ненужные технические сведения; детальные доказательства остаются в local/.
Экспортированные листы модели не заменяют PDF с оценкой и замечаниями.
Перед выдачей отрендерить и визуально проверить все страницы отчёта.
Файл отчёта и исходные данные хранить в local/<review-id>/; новую редакцию
выдавать отдельным файлом, не переписывая исторические отчёты и оценки.
Вопрос о допустимости другого балла не считать утверждением его замены;
при подготовке PDF сохранять зафиксированный балл до явного решения.

Для каждого критерия указать ID и источник, область проверки, статус,
ожидаемое и фактическое состояние, единицы/допуск, затронутые `UniqueId`
и ссылки на сохранённые доказательства. Для результата по всей категории
фиксировать размер выборки и полноту её обхода; единичный пример не доказывает
полное соответствие модели. Результат «0 элементов» оценивать по требованию
задания, а не автоматически как успех.

Сводка отдельно показывает подтверждённые нарушения, выполненные требования,
неприменимые критерии, непроверенные пункты и вопросы эксперту. Баллы,
веса и итоговый порог допустимы только по заданному профилю; неполнота
проверки не должна скрываться за общим процентом. Итоговый статус модели
не равен кадровому решению.

Реальные данные кандидатов и отчёты остаются в игнорируемом `local/`.
В общие правила переносить обезличенные решения с источником и областью
применения. Изменение критерия создаёт новую версию; старые отчёты сохраняют
свою версию. Проверки с исполняемым кодом добавлять в `src/` этого слоя
и проверять синтетическими примерами в `tests/` по мере появления критериев.
