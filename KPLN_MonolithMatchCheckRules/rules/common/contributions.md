# Доработки сотрудников: отдельно от общей версии

Этот порядок применяется, когда при проверке объекта Codex исправляет или
дополняет расчёт, импорт, фильтрацию, группировку, отчёты, тесты или правила.
Разработка для текущей задачи допускается в пределах поручения пользователя.
Она не означает разрешения распространять изменения на всех сотрудников.

## Рабочая копия и исходная версия

До первой правки сохранить версию общих правил, Git commit кода (если он есть)
и SHA-256 затрагиваемых исходных файлов. Если расчётный код не входит в общий
пакет, отдельно записать его источник и снимок. Версия правил не заменяет
версию движка. Отсутствующую исходную версию обозначить явно, не придумывать.

Изменения делать в отдельной локальной рабочей копии. Если используется Git,
создать свою ветку `codex/<краткое-имя-доработки>` в этой копии, не переключать
ветку общего сетевого checkout. Без Git сохранить исходные и изменённые файлы
с относительными путями. Не редактировать неизменяемый rules_snapshot запуска.
Нужную поправку оформить как отдельную версию/надстройку рабочего кода с хешами.

При обычной проверке не перезаписывать общие `rules`, `engine`, `scripts`,
`skills`, `VERSION` и принятые материалы других сотрудников. Не менять их
права доступа и не заменять общий пакет своей копией. Изменение геометрии,
единиц, допусков или исключений нельзя выдавать за простое ускорение.

## Пакет на рассмотрение

Сохранять пакет в общей папке:
`local/contributions/YYYY.MM.DD_<operator>_<project>_<unique-id>/`
относительно KPLN_MonolithMatchCheckRules. Дата — по времени Москвы,
unique-id — UUID; каталог создаётся новым, без перезаписи чужих материалов.
Не использовать имена/пути с выходом за этот каталог. Каталог `local/`
исключён из Git: предложение не становится принятой версией от одного сохранения.

Если общей папки нет или запись недоступна, сохранить пакет и очередь локально.
Технический путь записать в служебный журнал; пользователю сообщать о сбое,
только если он мешает получению результата или требуемой общей публикации.
Не писать, что пакет опубликован, до успешного копирования и сверки хешей.

Состав пакета:

- `REVIEW.md` по [шаблону](../../examples/contribution-review.md): автор,
  проект/стадия/корпус, исходная версия, проблема, изменение, результаты,
  ограничения и точные команды воспроизведения.
- `manifest.json`: ID предложения, время, статус `pending_review`, базовые
  версии/хеши, список добавленных/изменённых/удалённых относительных путей,
  SHA-256 исходных и новых файлов, зависимости и ссылки на запуски.
- `before/` и `after/` с затронутыми файлами либо доступный базовый Git commit
  и полный diff. Новые и неотслеживаемые файлы включать обязательно; бинарные
  изменения передавать файлами или бинарным diff. Удаления перечислять явно.
- `tests/`: команды, коды завершения и журналы выполненных проверок. Отличать
  тесты кода от сверки с моделью и реального импорта в плагин. Не выполненное
  обозначать `not_run` с причиной, не записывать как успешное.
- `evidence/`: минимальные примеры «до/после» или ссылки на доступные общие
  результаты. Указать, какие ложные/пропущенные замечания проверены и какие
  случаи остаются неподтверждёнными. Процент точности не заявлять без измерения.

Не копировать в пакет пароли, ключи, личную историю чатов, чужие настройки
приложений и большие NWD/кэши. Для моделей и результатов дать общий путь и хеш;
локальный путь автора сам по себе не делает данные доступными проверяющему.
Сохранить контрольную точку пакета перед завершением или паузой разработки.
Путь пакета и перечень изменений записать в служебный журнал. Показывать их
по запросу BIM-менеджера или сотрудника, не добавлять технический отчёт к
каждому обычному результату проверки.

## Применение и включение

Доработку можно использовать в своей проверке, не ожидая включения в общий
пакет, если она соответствует заданию и прошла необходимые для неё проверки.
Запуск должен записывать ID предложения, базовую версию и хеш применённого кода.
Непроверенный результат остаётся предварительным. Выпуск и запись в основной
реестр допускаются только после обычной приёмки из process.md и history.md;
создание пакета предложений не разрешает обход этих условий и не создаёт
отдельный основной реестр сотрудника.

Другие проверки не подхватывают `pending_review` автоматически. Включение в
общую версию — отдельная задача по явному поручению пользователя/ответственного
за общую версию: разобрать diff и доказательства, согласовать конфликтующие
доработки, проверить регрессии и применимость к другим проектам. Затем сохранить
резервную копию, обновить VERSION/CHANGELOG и записать решение о предложении
(`accepted`, `rejected` или `needs_changes`) с причиной и версией включения.
Если решение пригодно только указанному проекту, использовать `project_only`
с явной областью. Порядок автоматического повторного использования собственных
доработок и поведения при сбое сети — [local-first.md](local-first.md).
Исходное предложение сохранять для истории. Частичное включение перечислять
по файлам/изменениям. Проектные исключения не превращать в общие правила.

Это инструкция для Codex, а не техническая блокировка сетевых прав и не
автоматическая система Git review. Уже идущие чаты со старым снимком правил
не получают её задним числом; для них требуется отдельное указание прочитать
этот порядок без замены геометрического профиля текущего расчёта.
