# Navisworks 2020 → MCP мост (Clash Detective)

## Трубы и перекрытия: геометрия проходов

Дополнительная версия `SlabGeometryVersion=pipe-slab-mesh-1`, MCP:
`SlabMetricsVersion=pipe-slab-mesh-1`. Версии воздуховодов `duct-footprint-6`
и точного сечения `object-section-1` сохранены.

При запросе метрик для пары `Трубы`/`Перекрытия` доступны `PipeSlabGeometry`,
`SlabPipeAxis`, `SlabNormal`, `SlabNormalAngle`, `SlabEdgeContact`,
`SlabFullSectionCovered`, `SlabOuterDiameterMm`, `SlabThicknessMm`,
`SlabPipeLengthMm`, `SlabSections`, `PipeId`, `SlabId`, `GroupId` и
`GroupIdentityKnown`. В исходном DTO длины в футах, нормализованные контуры —
в миллиметрах. Известный null GroupId означает одиночный результат; неизвестный
идентификатор не разрешает объединять результаты по совпадению имени группы.

Ось подтверждается цилиндрическими поверхностями/кольцами трубы, включая
короткие и полые трубы. Проверяется замкнутость сетки плиты, широкие поверхности
и контакт наружного контура трубы с боковыми гранями, включая отверстия.
Сложные/ступенчатые плиты и неподтверждённые цилиндры возвращают причину отказа,
а не ось по габариту. Матрицы экземпляров проверяются существующим механизмом.
Пороги отверстий, пучки и статусы остаются в KPLN_NavisClashRules.

Проверка: `dotnet run --project tests/PipeSlab/PipeSlab.csproj` и
`python -B -m unittest discover -s tests -v`.
После сборки требуется перезагрузка аддона в Navisworks и отдельный перезапуск
MCP. Старые загруженные процессы новых полей не выдадут.

Для стен добавлены `Item1DuctSection` / `Item2DuctSection` и маркер
`DuctSectionVersion=object-section-1`. Прямой воздуховод: `Объект` ->
`Высота` + `Ширина` или `Диаметр`. Изоляция: `Размер воздуховода` плюс
две толщины. Отсутствующие точные свойства остаются неизвестными.
Для этого контракта требуется пересборка аддина и перезапуск обоих процессов.

Статус: **v0.3** — теперь как проект Visual Studio (`KPLN_NavisMcpBridge.sln`).
Собран и переписан по итогам двух раундов декомпиляции ваших реальных DLL —
сначала `Autodesk.Navisworks.Api.dll` и `Autodesk.Navisworks.Interop.ComApi.dll`,
потом ещё и `Autodesk.Navisworks.ComApi.dll` (третья сборка, которую вы сами
нашли и докинули). Сети в песочнице нет (pip/npm/apt заблокированы), поэтому
готового декомпилятора поставить было нельзя — написал свой минимальный
парсер метаданных ECMA-335 на чистом Python и вытащил реальные имена
классов/методов/сигнатур прямо из ваших DLL. Ошибка сборки, которую вы
прислали (`RunTest` требует аргументы), тоже отсюда — я изначально не
досмотрел его параметры, теперь поправлено и перепроверено.

## Как открыть в Visual Studio

Просто откройте `KPLN_NavisMcpBridge.sln` — там один проект (`addin\KPLN_NavisMcpBridge.csproj`).
**F5 запускает Navisworks и сразу цепляет отладчик** (настроено в
`addin\KPLN_NavisMcpBridge.csproj.user`) — можно ставить breakpoint'ы прямо в
`ClashService.cs`. После каждой сборки (в т.ч. по F5) DLL и манифест сами
копируются в bundle-папку `%ProgramData%\Autodesk\ApplicationPlugins\KPLN_NavisMcpBridge.bundle\`
(таргет `DeployBundle` в .csproj) — руками копировать не нужно.

Если Copy в `DeployBundle` падает с "отказано в доступе" — запустите Visual
Studio от администратора (первое создание папки в `%ProgramData%\Autodesk\...`
иногда требует прав, дальше обычно уже нет).

Если F5 не запускает Navisworks — я предположил, что exe называется
`Roamer.exe` (историческое имя для Navisworks), но **это не проверено**
(это не .NET-сборка, декомпилировать нечем). Гляньте, на что ссылается ваш
ярлык "Navisworks Manage 2020" (правой кнопкой → Свойства → Объект) и
поправьте `StartProgram` в `KPLN_NavisMcpBridge.csproj.user`.

## Три DLL нужны в корне подключённой папки

Сейчас у вас там `Autodesk.Navisworks.Api.dll` и `Autodesk.Navisworks.ComApi.dll`
— не хватает третьей, **`Autodesk.Navisworks.Interop.ComApi.dll`** (её вы
раньше присылали мне в чат, 310 072 байт) — она держит все `Inw*`-интерфейсы
(`InwOpState10`, `InwOclClashTest` и т.д.), без неё сборка не найдёт эти
типы. Скопируйте её из `C:\Program Files\Autodesk\Navisworks Manage 2020\`
туда же, где лежат две другие (`X:\BIM\5_Scripts\Git_Repo_KPLN\KPLN_NavisMcpBridge\`).

## Главное открытие раунда 1: в Navisworks 2020 нет managed Clash API

`Autodesk.Navisworks.Api.Clash` (управляемый API для Clash Detective)
появился в SDK **позже** 2020 года. `Document.Clash` в вашей версии
возвращает `IDocumentClash` — пустой интерфейс-заглушку без единого метода.
Так же пусты `IDocumentTimeliner` и `IDocumentTakeoff`. Реальный Clash
Detective доступен только через **COM API** (`Interop.ComApi`).

## Главное открытие раунда 2: ComApiBridge всё-таки существует

Сначала я не нашёл публичный класс `ComApiBridge` (только внутренний,
но тоже публичный `Autodesk.Navisworks.Internal.ApiImplementation.ComApi.Bridge`
внутри `Api.dll`) и работал через него. Когда вы прислали третью DLL —
`Autodesk.Navisworks.ComApi.dll` — в ней нашёлся настоящий, "канонiчный"
`Autodesk.Navisworks.Api.ComApi.ComApiBridge` со строго типизированным
`State` (сразу `InwOpState10`, без каста) и, что особенно ценно,
`ComApiBridge.ToModelItem(InwOaPath)` — конвертирует путь клэша в обычный
managed `ModelItem`. Код теперь использует именно его вместо ручного обхода
COM-дерева узлов.

Цепочка вызовов в `addin/ClashService.cs`:

```
ComApiBridge.State                        // сразу InwOpState10, каста не нужно
  .Plugins()                              // InwPluginsColl (метод, не свойство!)
    → перебор, cast к InwOpClashElement   // корневой объект Clash Detective
      .Tests()                            // InwClashTestsColl (метод!)
        → InwOclClashTest                 // .name, .status, .RunTest(0,null), .results()
          .results()                      // InwTestResultsColl (метод!)
            → InwOclTestResult            // .name, .status, .distance, .Path1/.Path2, .Comments()
              → ComApiBridge.ToModelItem(Path1/Path2) → ModelItem.AncestorsAndSelf
```

## Важная деталь стиля этого COM API

Часть членов интерфейса — это методы БЕЗ префикса `get_`, хотя выглядят
как свойства: `Plugins()`, `Tests()`, `results()`, `Comments()` — их нужно
вызывать со скобками. Другая часть — настоящие C#-свойства: `.name`,
`.status`, `.distance`, `.Path1`, `.Path2`. Перепутать легко, в коде это
откомментировано на каждом вызове.

## Что подтверждено декомпиляцией (можно доверять)

- `InwOclClashTest.RunTest(int test_ndx, object ovProgress)` — **не** без
  параметров, как я думал сначала (отсюда была ошибка сборки CS7036).
  Смысл `test_ndx` на объекте-тесте (а не коллекции) неясен из одних
  метаданных — похоже на неиспользуемый параметр общего шаблона; вызываем
  как `RunTest(0, null)`.
- Статусы теста: `nwEClashTestStatus` = NEW / OLD / PARTIAL / OK.
- Статусы результата: `nwETestResultStatus` = NEW / ACTIVE / APPROVED /
  RESOLVED / REVIEWED / UNMERGED (у результата, не у теста).
- У тестов и результатов **нет Guid** — только `.name` (строка). MCP-тулы
  идентифицируют тест/результат по имени.
- `ComApiBridge.ToModelItem(path)` → обычный `ModelItem`, дальше стандартный
  managed API (`.AncestorsAndSelf.Select(a => a.DisplayName)`).
- Комментарии к результату: `result.Comments()` → `InwCommentsColl`, каждый
  элемент — `InwOpComment` с `.Body`, `.User`, `.Date`.
- Коллекции (`InwClashTestsColl`, `InwTestResultsColl`, `InwPluginsColl`,
  `InwCommentsColl`) реализуют `InwCollBase` → `System.Collections.IEnumerable`
  — обычный `foreach` работает.

## Что осталось непроверенным (нужен реальный запуск)

1. **Как находится сам элемент Clash Detective среди `State.Plugins()`.**
   В 2020 нет метода `GetPlugin(id)` по строковому имени — код перебирает
   все плагины документа и берёт первый, что приводится к
   `InwOpClashElement`. Должно работать независимо от точного имени
   плагина, но не проверено запуском.
2. **Добавление комментария** реализовано через managed API 2020:
   `Document.CreateCommentWithUniqueId` и `TestsEditResultComments`.
   Сборка и автоматические проверки не заменяют проверку в живом Navisworks.
3. **Экспорт отчёта** — не реализован, вернёт 501. Вероятный путь —
   `State.DriveIOPlugin(pluginName, filePath, options)`, но точное имя
   IO-плагина отчёта Clash Detective не определить статически.

Экспорт отчёта остаётся недоступным; комментарии требуют обновлённого аддона.

## MCP-тулы (server/navis_mcp_server.py)

- `get_bridge_health()` — быстрая диагностика доступности локального HTTP-моста и Clash Detective
- `get_clash_test_overview(test_name)` — карточка теста: статус, ResultCount, tolerance, тип
- `get_clash_status_summary(test_name)` — компактные счётчики статусов результатов без путей и геометрии
- `list_clash_tests()` — имя, статус, число результатов по каждому тесту
- `get_clash_test_results(test_name)` — результаты теста
- `run_clash_test(test_name)` — пересчитать тест
- `set_clash_result_status(test_name, result_name, status, comment="")` —
  статус (New/Active/Approved/Resolved/Reviewed) и необязательный комментарий
  в одной транзакции; статус относится к коллизии, комментарий — к её группе
  (либо к самой коллизии, если она одиночная); прежние комментарии сохраняются
- `batch_add_clash_result_comments(test_name, result_names, comment)` —
  одинаковый текст группам или одиночным результатам без изменения статусов
- `get_clash_comment_targets(test_name, result_names)` — прочитать фактических
  адресатов и их комментарии, не меняя модель
- `export_clash_report(test_name, format="html")` — пока не реализовано

## Пакетные комментарии

`POST /clash/results/{testName}/comments` принимает
`{"resultNames": ["Конфликт1", "Конфликт2"], "comment": "Точный текст"}`.
Это один запрос и одна транзакция на главном потоке. Метод не выбирает
результаты по статусу: сначала прочитайте актуальные результаты, затем передайте
проверенный список имён. Если у результата есть группа, комментарий добавляется
ближайшей родительской `ClashResultGroup`; если нет — самому результату.
Родитель определяется через API, а не из текстового `Group`. Несколько
выбранных коллизий одной группы дают одну запись. Группы различаются по Guid,
поэтому одноимённые группы не объединяются.

Старые комментарии копируются, новый получает уникальный ID документа и
текущего автора Navisworks. Статус самого комментария New не меняет статус
коллизии. Совпадение полного текста (с учётом регистра, пробелов и переносов)
с существующим комментарием фактического адресата пропускается. Это позволяет безопасно
повторить тот же запрос после проверки результата таймаута.
Старые комментарии дочерних коллизий не удаляются, не переносятся автоматически
и не мешают добавлению того же текста в группу. Комментарий группы не копируется
в дочерние коллизии. В смешанной по статусам группе меняется только комментарий
группы; статусы всех детей сохраняются.

Ответ: `updated`, `unchanged`, `failed` (исходное имя результата -> полный текст ошибки)
и `targets`. Для совместимости первые списки относятся к исходным именам
коллизий, а не к количеству комментариев. `targets` содержит фактические
записи: `kind` (group/result), `name`, `id`, `result_names`, `comments`,
`outcome` (updated/unchanged/failed), `error`. Число новых комментариев —
число адресатов с `outcome=updated`. Ошибка группы сообщается для каждого
выбранного результата этой группы.
MCP преобразует `failed` в список `{result_name, error}`. Пустой текст/список
даёт 400, ненайденный тест/результат 404, неоднозначное имя результата 409.
Имена проверяются до записи всего пакета. Ошибки отдельных записей не
отменяют успешные; ошибка общей транзакции возвращается как ошибка запроса.
Комментарий в пакетной смене статусов не поддерживается: используйте отдельную
команду комментариев.

Для предварительной проверки адресатов и чтения после записи:
`POST /clash/results/{testName}/comment-targets` с `{"resultNames": ["Конфликт1"]}`
(операция только чтения), MCP-команда `get_clash_comment_targets`.
Поле `Comments` в `get_clash_test_results` по-прежнему показывает только
собственные комментарии коллизии, без подмешивания комментариев группы.
Логика записи выделена в `addin/ClashService.Comments.cs`; остальные
операции ClashService не меняют правила адресации статусов.

После обновления: пересобрать аддон, перезапустить Navisworks и включить MCP
Bridge; перезапустить MCP-сервер/его подключение в Codex для новой команды.
В живом Navisworks проверить сохранение старого текста и статуса, точный текст
нового комментария через `get_clash_comment_targets`, отсутствие дубля при повторе,
затем сохранение NWF и повторное открытие. Не запускать Clash Detective заново.

Тесты транспорта (окружение с `server/requirements.txt`):
`python -m unittest discover -s tests -p "test_*.py"`.
Тесты C# логики адресатов, сохранения статусов и ошибок на API-двойниках
(выполняют производственный `ClashService.Comments.cs`, требуют .NET 8 SDK):
`dotnet run --project tests/CommentRouting/CommentRouting.csproj`.
Они не заменяют проверку native API в живом Navisworks.

### Mesh-направление каркаса и отношение к стене

При `includeItemBounds=true` и `includePaths=true` HTTP-мост возвращает
`Item1AxisGeometry`/`Item2AxisGeometry` для несущего каркаса (категория
`Каркас несущий`/`Structural Framing` или семейство `НесКаркас_Балка`).
Профнастил/deck исключён из извлечения оси балки. Это распознавание каркаса,
не проверка материала стали; материал и продольность оценивает вызывающий анализ.
В MCP оба флага автоматически включаются через `include_metrics=True`.

Ось вычисляется по треугольникам реальной геометрии с преобразованием в мировые
координаты, а не по габариту или направлению диагонали AABB. PCA использует
интегралы по площади поверхности, поэтому разная плотность триангуляции не
смещает ось. Это 3D-ось: учитываются наклон, вертикаль и знаки компонент.
Результаты, включая отказы, кешируются по полному COM-пути экземпляра в пределах
одного запроса. Кеш mesh стены также использует полный путь, а не InstanceGuid.

Поля DTO: `Axis` (единичный вектор; v и -v эквивалентны), `Center` (центр масс
поверхности), `Length`, `TransverseSize` (в футах), `Reliability` (отношение двух
главных собственных значений), `TriangleCount`, `Source`, `Usable`, `Reason`.
`Usable` требует выраженной оси: Reliability >= 4 и продольный размер >= двух
поперечных. Это техническая проверка устойчивости PCA, не правило допуска.
Она не доказывает прямолинейность сложного семейства и не измеряет фактическую
длину пересечения со стеной.

Неполная геометрия/лимит 30000 вершин выбранного экземпляра, составной узел с несколькими геометрическими
элементами, ошибка COM, несоответствие мирового bbox и неоднозначная матрица
возвращают `Usable=false` с причиной. Конвенция матрицы проверяется по мировому
bbox; если обе конвенции подходят, но дают разные оси, результат отклоняется.
При COM-ошибке `Reason` содержит полный текст исключения.

`Fragments()` возвращает фрагменты всех экземпляров общего узла. Перед чтением
матриц и треугольников мост сравнивает полный `fragment.path.ArrayData` с путём
запрошенного геометрического элемента. Чужие экземпляры не расходуют лимит и не
попадают в PCA. Фильтрация применяется к каркасу и стенам. Неизвестный путь или
отсутствие совпавших фрагментов не допускают перехода к геометрии всего узла.
Это учитывает [описанное Autodesk поведение COM API](https://forums.autodesk.com/t5/navisworks-api-forum/geometry-primitive-returns-multiple-objects/m-p/10441638/highlight/true).

Мировой bbox для проверки преобразования собирается из `GetWorldBox()` только
совпавших фрагментов. Исходный `Item*Bound` не переписывается: он сохраняется
в диагностике для сравнения, но не используется вместо bbox выбранного mesh.
Поле `Item*AxisGeometry.Diagnostics` содержит полный путь экземпляра,
`MatchedFragments`, `SkippedInstanceFragments`, `GeneratedTriangleCount`,
`PointLimit`, `ReportedItemBounds`, `SelectedFragmentBounds`, `RowMeshBounds`,
`ColumnMeshBounds`. При превышении лимита причина `mesh-point-limit`, при
нечитаемой вершине `mesh-invalid-vertex`; оставшиеся ошибки bbox по-прежнему
отклоняются, а не маскируются увеличенным допуском.

`GeometryVersion=instance-mesh-2` подтверждает загрузку нового аддона.
`MetricsVersion=frame-mesh-2` в ответе с `include_metrics=True` подтверждает
новый Python MCP-процесс. Если есть первое поле, но нет второго, необходимо
перезапустить MCP-сервер: rebuild аддона не обновляет уже импортированный Python.

Для каркаса со стеной MCP возвращает `FrameWallNormalAngle` (также
`WallNormalAngle`): 0 градусов поперёк стены, 90 в её плоскости. Стена берётся из
существующего mesh-PCA, каркас только из новой mesh-оси. Также доступны
`FrameAxis`, `FrameAxisSource`, `FrameAxisReliability`, `FrameAxisReason`,
`FrameLengthMm`. Данные оси сохраняются при удалении сырых bounding boxes из
ответа. Без надёжной оси любой стороны угол null и `GeomOk=false`; старый аддон
также не приводит к подстановке направления каркаса из AABB. Метрики трубы и
отверстия (`Angle`, `PerpRel`, `Dia`, `Len`, `Elong`, `SectionMax` и др.) для
каркаса не вычисляются. Остальные пары труб/воздуховодов не изменены.

Геометрические тесты: `dotnet run --project tests/FrameGeometry/FrameGeometry.csproj`.
Тесты MCP входят в общий `python -m unittest discover -s tests -p "test_*.py"`.
После установки требуется пересборка аддона, перезапуск Navisworks с включением
MCP Bridge и перезапуск процесса MCP. Проверка в живой модели необходима:
проверить ось эталонной балки и поперечного примера. Новые поля ничего не меняют
в статусах, группах или комментариях; перезапуск Clash Detective не требуется.

### Сечение воздуховода против потолка

При чтении геометрии прямого воздуховода категории `Воздуховоды`/`Ducts`
или `Материалы изоляции воздуховодов`/`Duct Insulations`
с потолком `Потолки`/`Ceilings` аддон возвращает `DuctCeilingFootprint`.
Геометрия каждого участника фильтруется по полному пути экземпляра и кешируется
в пределах запроса. Воздуховод пересекается с ближайшей широкой mesh-поверхностью
потолка; полученный прямоугольный или круглый контур обрезается треугольниками этой поверхности.
Площадь учитывает частичное перекрытие и отверстия в потолке. `Bound` коллизии
не используется. Поворот в плане и наклон потолка учитываются в его плоскости.

DTO содержит `Usable`, `Reason`, `DuctSide`, `Normal`, `PlaneOrigin`, обе стороны
`MinEdge`/`MaxEdge` в футах, `Area` и `DuctSliceArea` в квадратных футах.
`Source=duct-ceiling-mesh-section`.
Для обычного воздуховода сечение читается из числовых свойств
`Объект -> Высота + Ширина` либо `Объект -> Диаметр`; строка `Размер` не нужна.
Для изоляции парсится `Объект -> Размер воздуховода`: поддерживаются `150x500`
и `ø100`. К номинальным граням или диаметру добавляются две толщины изоляции
из `КП_И_Толщина стенки`/`Толщина изоляции`/`Insulation Thickness`, чтобы
сравнение выполнялось с внешним mesh-контуром изоляции.
Неоднозначная плоскость,
неполный mesh и несовпадение мировых габаритов возвращают причину отказа.
Выпуклая оболочка используется для сечения одного прямого воздуховода; это не
универсальный Boolean произвольных solids и не расчёт объёма коллизии.

MCP сравнивает обе стороны прямоугольника либо диаметр круга и площадь с контуром:
по каждой стороне/диаметру `max(2 мм, 2%)`, по площади 2%. Перестановка сторон допустима;
разные сечения перехода и отсутствующее свойство не подменяются
габаритами. `DuctSectionFootprintMatch=true` и
`DuctCeilingRelation=transverse-by-section` означают поперечность по сечению.
Несовпадение не доказывает продольность. `MepAxis` по этому сравнению не выдумывается.
Для этой пары старые AABB-метрики оси трубы не применяются.

`ClashFootprintMinMm`, `ClashFootprintMaxMm`, `ClashFootprintAreaMm2`,
`DuctSectionAreaMm2`, `DuctSectionEdgeErrorsMm`, `DuctSectionAreaErrorRatio`
и поля допусков раскрывают сравнение. `GeomOk=true` здесь означает подтверждённое
совпадение сечения, а не назначение статуса. В общем классификаторе потолков
подтверждённый поперечный проход прямоугольного/круглого воздуховода или его изоляции получает Approved
по уточнённому пользователем правилу. Статусы этот расчёт не меняет.

`FullDuctSectionCovered` с погрешностью 2% проверяет, что потолок покрывает весь срез воздуховода,
а не только участок, случайно совпавший с номинальным сечением.
`DuctSliceAreaMm2` раскрывает площадь полного среза. Неполный контур и отверстия
не подтверждают нормальный проход.

При чтении каждого фрагмента проверяются экземпляр, аффинность матрицы и
попадание всех вершин в его мировой бокс. Точное равенство крайних координат
не требуется: бокс может быть консервативным для повёрнутой сложной формы.
Неоднозначное преобразование и вершины вне бокса остаются ошибкой.
Фрагменты без треугольных поверхностей (например, вспомогательная осевая линия)
пропускаются; хотя бы один полноценный mesh-фрагмент остаётся обязательным.
`DuctMeshDiagnostics` и `CeilingMeshDiagnostics` внутри `DuctCeilingFootprint`
содержат матрицы, боксы, число треугольников и выбранное преобразование,
включая данные при отказе чтения.

Текущие версии: `GeometryVersion=duct-footprint-6` и `MetricsVersion=duct-footprint-6`.
После rebuild перезапустить Navisworks и MCP-процесс. Проверить живой пример
с номинальным сечением и сопоставить площадь/обе стороны перед массовой записью.
Тесты: `dotnet run --project tests/DuctFootprint/DuctFootprint.csproj`,
а также общий Python unittest-набор.
